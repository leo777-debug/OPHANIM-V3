# API keys and external services

Generated by `node scripts/generate-api-inventory.mjs` from source identifiers, never secret files.

Fill credentials only in uncommitted `.env` or the hosting dashboard, then restart the service. Next.js also reads `.env.local`; existing values there take precedence over `.env`, so consolidate duplicate settings deliberately. Admin → Integrations shows presence, never values. This release uses environment-only configuration; there is no browser credential store or UI secret-saving endpoint.

Pricing/quotas vary by plan and may change. “Keyless” describes access, not commercial redistribution permission. Reserved adapters are explicitly marked; adding a variable does not implement an adapter. Missing keys do not create observations or live status.

## Scope and configuration notes

- Supabase accepts `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` aliases. Only publishable keys may use the public prefix. Backend keys remain server-only.
- VoidAccess requires its URL plus either a bearer token or email/password service account.
- Local compatible AI can run without an API key when its base URL is explicitly allowed. Hosted AI normally needs a key.
- `EMBEDDING_API_KEY`, customer feed tokens and source licences depend on the chosen provider.
- Commercial-use decisions for new connectors must be explicit in the provider registry. Unknown and disallowed rights default off. Existing sources still need the per-feed audit recorded in PARITY.
- Connection tests show exactly what was checked. A configured credential is not a successful fetch. No test sends email, starts research or submits a scan.
- Planned P2 sources (ACLED, GNSS, radiation, population grids, tariffs, procurement and crowd forecasts) have no invented API variables or adapters. Add them here with their original documentation when implemented.
